# 合宙 780 系列模组 AI 通信工作站架构探索与技术选型

本文档完整沉淀关于“基于合宙 Air780EPV 模组构建个人通信工作站与接入 AI 能力”的架构思考、硬件事实分析、死锁风险排查与落地路径设计。

---

## 一、 核心定位与设计原则

### 1.1 单片机硬件现实（为什么不能做“微型电脑”）
- **资源限制**：移芯 EC718P-V 芯片给 LuatOS 可用的堆内存（RAM）仅约 300KB ~ 400KB，可写 Flash 仅约 1MB。
- **Flash 磨损寿命**：频繁落盘、修改海量短信历史会导致 Flash 寿命加速耗尽，且内存无法支撑复杂的文本搜索与分页。
- **4G 网络单向屏障（CG-NAT）**：板卡分配的是运营商大内网 IP（如 `10.x.x.x`），外界无法直接发起 HTTP 连接访问板载 Web，内网穿透耗费额外资源与电量。
- **架构定调**：
  > **板卡绝不做“数据中心与应用服务器”，板卡的终极定位是纯粹的“蜂窝无线电外设与信令执行器”。**
  > 界面渲染、业务逻辑、数据库存储、AI 大脑全部交由外部宿主（PC 或云端）承担。

## 二、 赋予 AI 物理蜂窝通信能力（AI Agent + SIM）

### 2.1 体系三层分工
```text
┌────────────────────────────────────────────────────────┐
│                   1. 大脑与意图层 (AI Agent)           │
│  • 理解自然语言意图（“帮我查昨天扣费”、“回复退订”）     │
│  • 负责多轮对话、参数提取、决策与工具调用 (MCP / Tool)    │
└───────────────────────────▲────────────────────────────┘
                            │ 标准 Function Call (JSON)
┌───────────────────────────▼────────────────────────────┐
│                2. 记忆与中枢层 (Database)               │
│  • 解决“板子存不下”的痛点：海量短信云端/本地结构化落盘   │
│  • 载体：飞书多维表格 (Bitable) 或 本地 SQLite          │
│  • 提供时间线过滤、全文检索、向量语义检索                │
└───────────────────────────▲────────────────────────────┘
                            │ 通信总线 (串口 / MQTT)
┌───────────────────────────▼────────────────────────────┐
│               3. 物理执行层 (Air780EPV 板卡)            │
│  • AI 的“射频机械臂”：纯粹的调制解调器 (Modem)          │
│  • 核心原始原子能力：`send_sms`、`on_sms_inc`、`call`    │
└────────────────────────────────────────────────────────┘
```

### 2.2 核心场景落地逻辑
1. **“让 AI 查之前发送/收到了什么短信”**：
   - 短信进入时由中枢入库，AI 直接使用 SQL 或检索工具查询中枢数据库，进行数据阅读理解、聚合统计并用自然语言回答（甚至支持模组离线时查询）。
2. **“让 AI 帮我发送一条短信”**：
   - 用户自然语言表达诉求 -> AI 解析出目标号码与短信正文 -> AI 触发 `send_sms(to, text)` 工具 -> 中枢下发给板卡射频发射 -> 基站确认后向 AI 返回执行回执。

## 三、 运行形态、死锁风险与利弊剖析

### 3.1 4G 无线独立模式（免插电脑，插充电头）
- **通信通路**：板卡主动向云端建立 MQTT / TCP 出向长连接（每天保活心跳流量 < 500KB）。
- **致命死锁风险（0 流量陷阱）**：
  - **现象**：当 SIM 卡欠费、无流量包或被断网时，用户面（IP 网络）完全断开，MQTT 无法接收指令。
  - **死锁**：用户无法通过网络给板子下发“发送 10010 查话费/办流量包”的指令；板子无法发短信自救充值。
- **解死锁方案（信令面兜底）**：
  - 断网时，用户使用主力手机向板卡直接发送加密短信指令（走蜂窝信令通道，0 流量也能收到），板卡拦截指令并在本地代发。

### 3.2 本地 USB 模式（电脑作为 Host 宿主）
- **通信通路**：Type-C 数据线直接连接电脑虚拟串口（`COM7`），走标准 AT 指令或自定义串口协议。
- **关键认知澄清**：
  - **板卡无需跑任何 Web 或后端**，板卡就是个标准 USB 调制解调器；
  - **后端跑在电脑上**（如 Python 进程、标准 MCP Server），由电脑提供无限内存、海量磁盘和直连大模型的网络。
- **优势**：
  - **绝对免疫 0 流量死锁**：无论 SIM 卡是否断网欠费，电脑通过物理串口下发 AT 指令，短信信令照样发射；
  - **开发门槛极低**：无需云服务器、无需公网 MQTT、无需内网穿透。
- **代价**：依赖电脑开机运行。

### 3.3 理想架构思考：Wi-Fi + 4G 双模解耦
- **完美形态**：若设备同时具备 Wi-Fi 芯片与 4G 模组：
  - **Wi-Fi 通道**：连接家庭/办公室无线宽带，承担无限免费流量、本地局域网 Web 秒开访问、MQTT 永不断连；
  - **4G 通道**：彻底退回到纯粹的“短信/VoLTE 信令通道”，即使 SIM 卡 0 流量、一分不充，也能通过 Wi-Fi 指挥它收发信令。
- **生态对照**：市场上带 Linux 的随身 WiFi 棒（OpenStick）或 ESP32-S3 + 4G 双芯片板即为此形态。
- **当前映射**：手头的 Air780EPV 无 Wi-Fi 芯片，**电脑的 USB 口在物理上等同于它的“有线 Wi-Fi”**，完美弥补了这一硬件短板。

## 四、 推荐落地演进路线

1. **Phase 1（本地 USB + MCP 原生工具）**：
   - 编写本地 Python 宿主守护程序，对接 `COM7` 串口，封装为标准 MCP Server（提供 `send_sms`、`list_sms`、`get_signal` 工具）；
   - 搭配本地轻量 SQLite 记录短信流水，AI Agent 直接接管通信能力。
2. **Phase 2（按需扩展无线/飞书）**：
   - 在本地闭环验证完成后，若需脱离电脑，在现有固件中启用 MQTT 客户端，并设计信令短信作为断网兜底。
