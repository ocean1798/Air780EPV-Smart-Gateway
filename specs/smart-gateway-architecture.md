# Air780EPV 智能随身通信网关架构与实现规范

## 1. 架构定位与设计哲学

基于对移芯 EC718P-V 芯片底层内存与物理分区的实测事实（官方固件 LittleFS 用户空间固定为 **128KB**，Lua 可用堆内存固定为 **128KB**），系统推翻“魔改底层 C 分区”与“板端硬跑重度 Web”的过度设计方案，确立**“板端坚决做轻、防御性配置优先、按需激发能力、上位机承接交互”**的务实架构：

- **防御性配置（安全保号）**：随身上网（RNDIS 网卡）**默认彻底关闭**，杜绝 Windows 后台更新偷跑流量；
- **信令通信优先**：短信收取与来电拦截走纯信令通道，不依赖 4G 数据流量，卡内 0 流量亦可安全运行；
- **按需激活高阶外设**：需要电脑 4G 上网时，通过上位机一键动态点亮 RNDIS 网卡；
- **分工明确**：板端专注 4G 射频与脱机黑匣子（100 条防丢缓冲），复杂的界面渲染、海量历史归档（SQLite）与 AI Agent 对接全部交给宿主机（PC/NAS）。

## 3. 板端严密资源账本（确保永不爆仓）

在将 P0 ~ P3 全部加载到模组后的资源占用审计：

1. **Flash LittleFS 用户文件系统（总额 128 KB）**：
   - 基础配置文件（`fskv`）：~2 KB
   - 短信黑匣子（100 条短信环形队列）：~25 KB
   - 随身上网开关标志位：~0.5 KB
   - **合计常驻仅占用约 28 KB，剩余 100 KB（空闲率高达 78%）**！
2. **Lua 堆运行内存（总额 128 KB）**：
   - 业务状态机 + 短信与电话解析：~15 KB
   - 串口收发缓冲区 + 网络 HTTP 请求：~15 KB
   - **合计常驻仅占用约 30 KB，剩余 98 KB（空闲率高达 76%）**！彻底消除 OOM 隐患。
3. **宿主算力与海量存储（P4）**：
   - 运行在 PC / NAS 端，消耗电脑的 CPU、GB 级内存与硬盘，对单片机零负担。

## 4. 核心功能实现设计

### 4.1 通信感知与 0 话费来电拒接（P0）
- **短信捕获**：
  监听 `SMS_INC` 事件，提取发件人号码与正文，通过正则表达式：
  `local code = content:match("(%d%d%d%d%d?%d?)")`
  快速抽取出 4~6 位验证码，优先打包送入串口和飞书。
- **来电拒接**：
  监听 `CC_IND` 事件。一旦收到 `INCOMINGCALL` 振铃状态，立即执行两步原子操作：
  1. `local from = cc.lastNum()` 毫秒级提取号码并向飞书/串口发布事件；
  2. 立即执行 `cc.hangUp()` 主动拒接，**全程双方 0 话费，无任何音频处理开销**。

### 4.2 板载断网黑匣子持久化（P1）
- **存储文件**：`/sms_box.jsonl`（每行一条 NDJSON 记录，便于追加与切片）。
- **环形淘汰与 GC 协同算法**：
  - 内部计数器达到 100 条上限时，采用批次淘汰（批量淘汰前 20 条，重写剩余 80 条），减少 Flash 擦写频次；
  - 重写文件后，**必须显式调用 `collectgarbage("collect")`**，立即释放字符串重组产生的临时堆内存，将 Lua 堆稳定压制在 53KB；
  - 写入操作由底层 LittleFS 执行全局磨损均衡，单片机 NOR Flash 擦写寿命超 10 年。
- **流式防爆内存读取**：
  - 上位机请求拉取历史时，板端使用 `io.open` 逐行读取并输出，每次仅占用几百字节缓冲区，严禁一次性全量装入 Lua Table。

### 4.3 随身上网动态受控切换（P3）
- **启停控制与热复位时序**：
  在 EC718PV 芯片中，修改 USB 复合设备模式（CDC ACM + RNDIS）需要重新向 USB Host 声明设备描述符。采用“两阶段握手时序”：
  1. **第一阶段（即刻回执）**：板端收到 `{"cmd":"set_rndis","params":{"enable":true/false}}` 后，先向 `VUART_0` 用户虚拟串口返回响应帧 `{"type":"res","msg":"RNDIS_SWITCHING", ...}`，确保上位机收到确定性 ACK；
  2. **第二阶段（延时热复位）**：延时 500ms，板端执行 `mobile.config(mobile.CONF_USB_ETHERNET, enable and 1 or 0)` 并调用 `rtos.reboot()` 软重启；
  3. **上位机自愈重连**：PC 上位机后台线程捕获 USB 重新枚举引起的瞬断，并在设备重新就绪后无缝重连恢复通信。
- **安全保障**：开机初始化脚本中默认执行 `CONF_USB_ETHERNET = 0`，只有收到上位机明确命令时才临时开启。

### 4.4 串口通信协议（上位机直连接口）
板端与上位机通过 **USB 虚拟串口（VUART_0 用户口，Windows 下由动态探测定位如 `COM8`/`COM16`，Linux 下为 `/dev/ttyACM1`，`uart.VUART_0` ID: 32）**交互，采用行分隔 JSON（NDJSON，以 `\r\n` 结尾）：
- **分包粘包防护**：板端内置行累加器（`line_buffer`），只有收到完整换行符后才送入 `json.decode`，有效规避 USB CDC 块传输分包/粘包异常。
- **上位机串口参数**：波特率 115200、8N1，**打开端口后必须设置 `DTR=True` 与 `RTS=True`**，否则 CDC-ACM 不下发数据。

- **板端主动事件广播（模组 ➔ 上位机，`type: "event"`）**：
  - 网关就绪：`{"type":"event","event":"gateway_ready","data":{"bsp":"Air780EPV","csq":27,"temp":"37.00","vbat":"4.00","rndis":false}}\r\n`
  - 收到短信：`{"type":"event","event":"sms_rx","data":{"from":"+8613800138000","content":"...","code":"892104","time":1789008801}}\r\n`
  - 来电拦截：`{"type":"event","event":"call_rx","data":{"from":"+86138...","action":"REJECTED_ZERO_COST","time":1789008801}}\r\n`
  - 短信投递报告：`{"type":"event","event":"sms_tx_report","data":{"id":"cli_123","success":true}}\r\n`
  - 周期心跳：`{"type":"event","event":"status","data":{"csq":27,"rsrp":-89,"temp":"37.00","vbat":"4.00","rndis":false,"lua_mem_kb":53}}\r\n`

- **上位机下发指令与应答（上位机 ➔ 模组，`type: "cmd"` ➔ `type: "res"`）**：
  - 状态查询：
    - TX: `{"type":"cmd","id":"1","cmd":"get_status"}\r\n`
    - RX: `{"type":"res","id":"1","code":0,"msg":"STATUS_OK","data":{"bsp":"Air780EPV","csq":27,"rsrp":-89,"temp":"37.00","vbat":"4.00","blackbox_count":1,"rndis":false,"lua_mem_kb":53}}\r\n`
  - 发送短信：
    - TX: `{"type":"cmd","id":"2","cmd":"send_sms","params":{"phone":"13800138000","text":"验证码测试"}}\r\n`
    - RX: `{"type":"res","id":"2","code":0,"msg":"QUEUED_TO_BASE_STATION"}\r\n`
  - 查询黑匣子历史：
    - TX: `{"type":"cmd","id":"3","cmd":"get_history","params":{"limit":10}}\r\n`
    - RX: `{"type":"res","id":"3","code":0,"msg":"HISTORY_OK","data":{"count":1,"total":1,"items":[{"sender":"+86132...","content":"...","otp":"778899","time":1789008801}]}}\r\n`
  - 清空黑匣子历史：
    - TX: `{"type":"cmd","id":"4","cmd":"clear_history"}\r\n`
    - RX: `{"type":"res","id":"4","code":0,"msg":"HISTORY_CLEARED","data":{"total":0}}\r\n`
  - 控制随身上网：
    - TX: `{"type":"cmd","id":"5","cmd":"set_rndis","params":{"enable":true}}\r\n`
    - RX: `{"type":"res","id":"5","code":0,"msg":"RNDIS_SWITCHING","data":{"enable":true,"reboot_required":true}}\r\n`
  - 查询运行时间与自动重启状态 (P5)：
    - TX: `{"type":"cmd","id":"6","cmd":"get_uptime"}\r\n`
    - RX: `{"type":"res","id":"6","code":0,"msg":"UPTIME_OK","data":{"uptime_seconds":15,"reboot_hours":0,"next_reboot_seconds":-1}}\r\n`
  - 动态配置周期自动重启 (P5)：
    - TX: `{"type":"cmd","id":"7","cmd":"set_reboot_policy","params":{"hours":24}}\r\n`
    - RX: `{"type":"res","id":"7","code":0,"msg":"REBOOT_POLICY_UPDATED","data":{"reboot_hours":24,"next_reboot_seconds":86400}}\r\n`
  - 立即重启设备 (P5)：
    - TX: `{"type":"cmd","id":"8","cmd":"reboot","params":{"reason":"cli_reboot"}}\r\n`
    - RX: `{"type":"res","id":"8","code":0,"msg":"REBOOT_COMMENCED"}\r\n`

## 5. 典型运行拓扑

1. **PC 随身工作拓扑**：
   - 板子插在笔记本 USB 口，上位机常驻后台（右下角托盘）；
   - 平时：0 流量接收验证码和来电弹窗；
   - 紧急时：点击右下角“开启 4G 网卡”，笔记本直接获得网络。
2. **家庭 NAS 24 小时通信拓扑**：
   - 板子插在 NAS USB 口，NAS 启动 Python/Docker 守护进程监听串口；
   - 短信实时写入 NAS SQLite/数字资产数据库，通过家庭宽带转推 MQTT/微信；
   - 宽带断网时，NAS 可自动指令板端开启 RNDIS，作为家庭网络的 4G 逃生通道。
3. **AI Agent MCP 蜂窝物理化拓扑 (AIR-06)**：
   - 基于 FastMCP 协议栈落盘 `tools/mcp_server/server.py`；
   - 外部 Agent（Claude Desktop / Cursor / 工作区 Agent）通过标准 stdio JSON-RPC 接入；
   - 暴露 7 大物理工具：`get_gateway_status`, `send_sms`, `get_latest_otp`, `get_sms_history`, `clear_sms_history`, `toggle_rndis`, `reboot_gateway`；
   - 使大模型拥有真实世界 4G 蜂窝射频物理收发与验证码主动提取能力。

## 6. Web 控制台体系与底层协议栈技术定论 (AIR-10)

针对图形化管理控制台的工程实现与硬件物理边界，系统完成了双 Web 体系架构探索与移芯芯片底层协议栈逆向实测：

### 6.1 宿主端 Web 管理控制台（核心主力入口）
- **实现载体**：`tools/host_gateway/gateway_web.py`（监听 `0.0.0.0:17801`，一键启动批处理 `run_web.bat`）。
- **架构优势**：
  1. **零 4G 蜂窝流量开销**：宿主端 Web 完全基于宿主机（PC/NAS）的本地回环网络（`127.0.0.1:17800` Hub）与物理串口通信，彻底杜绝 Windows 开启虚拟网卡可能产生的偷跑流量；
  2. **自包含极简响应式 SPA**：零 npm/webpack 依赖，纯原生现代 HTML5/CSS3/ES6 编写，深色玻璃拟态质感，完美适配手机、平板与桌面浏览器；
  3. **实时全双工无刷新感知**：基于 HTTP Server-Sent Events (SSE) 协议，新短信接收、验证码提取与来电拦截毫秒级推流渲染，支持一键点击复制验证码；
  4. **硬件与保号双重防御切换**：界面直观提供 4G 随身网卡（RNDIS）与板载蜂窝数据（0 流量保号）的一键受控切换开关。

### 6.2 板载内嵌 Web 方案技术定论与退役归档（彻底定论：单 USB 裸板无法直连）
- **技术定论**：
  在单根 USB 线连接的 Air780EPV 裸板形态下，**“浏览器直连板载内嵌 Web”在物理与固件驱动层面被证明彻底不可行**：
  1. **物理拓扑边界**：板卡无 Wi-Fi、无以太网 RJ45，宿主机与模组之间仅有一条 USB 复合设备链路（CDC 串口或 RNDIS 网卡）；
  2. **纯串口模式（日常 0 流量保号态）**：PC 侧无虚拟网卡，无法承载任何基于 TCP/IP 协议的浏览器 HTTP 流量；
  3. **RNDIS 网卡模式（FastPath 硬件直通旁路）**：
     逆向 `luatos.elf` 与硬件抓包证实，移芯 EC718PV 芯片在固件底层通过 `NetifUlPkgFastPath` (`0x41c404`) 与 `PsifDlPkgFastPath` 实现了驱动级硬件加速。RNDIS 开启后，PC 发出的流量直接穿透到基站 WAN 侧或在驱动层被丢弃，根本不经过板端内嵌 LwIP 协议栈的上层输入处理，导致 PC 无法与板载 `httpsrv:80` 完成 TCP 三次握手；
  4. **体验与单片机资源严重劣化**：
     由于板载 Flash 上限仅 64KB，嵌入在 Lua 脚本内的 HTML 模板被极度压缩（<6.5KB），导致排版简陋拥挤、交互体验极差，与现代控制台形成巨大反差；同时额外占用了 10KB 宝贵的 Lua 运行堆内存与 6KB Flash 存储。
- **工程退役与裁剪决策**：
  - 彻底下线并从板载固件 Flash 中剔除 `web_service.lua`，回退网关固件至轻量纯净版，回收 10KB 运行 RAM 与 6KB 存储 Flash，单片机常驻堆内存降至 66KB（空闲率 48.4%）；
  - 将所有本地 mock 脚本（如 `preview_embedded_web.py`）及临时预览页面全部安全移入系统回收站；
  - 固化相关协议栈逆向分析、FastPath 旁路原理与避坑结论。
- **系统唯一权威架构入口**：
  **统一由宿主端 Web 管理控制台（端口 17801）作为核心图形化管理面板**，通过物理串口多路复用中枢（Hub）与网关模组通信，既享有现代化高颜值深色面板与毫秒级 SSE 推流，又坚决守住绝对 0 蜂窝流量与高可靠性的物理底线。

## 7. 关键工程课题分析与系统演进规范

针对网关在分发体验、多设备扩展、前端实时刷新、剪贴板交互以及多板硬件互联等 5 大核心演进课题，系统确立如下事实规范与工程演进标准：

### 7.1 软件分发与串口自适应探测架构（课题 1）
- **现象与问题**：
  上位机早期开发时曾硬编码 `SERIAL_PORT = "COM8"`。当软件分发给其他用户或设备拔插/复位漂移（如漂移至 `COM16`）时，写死 COM 口会直接导致上位机启动连不上硬件。当前已全面落地动态探测与自愈引擎。
- **Air780EPV 硬件串口特征**：
  - USB 厂商与产品 ID：`VID = 0x19D1, PID = 0x0001`（合宙/移芯官方 CDC-ACM 复合设备）；
  - 单个物理硬件在 Windows 下复合枚举出 **3 个独立虚拟串口**：
    1. `LOCATION=...x.2`：AT/日志口；
    2. `LOCATION=...x.4`：AP/调试口；
    3. `LOCATION=...x.6`：用户通信与虚拟串口（映射到 LuatOS `uart.VUART_0`）。
- **工程解法规范**：
  1. **双层自动扫描探测引擎**：
     - 第一层：通过 `serial.tools.list_ports.comports()` 遍历系统可用串口，基于 `VID=0x19D1, PID=0x0001` 自动圈定合宙模组候选端口列表；
     - 第二层：对候选端口发送非阻塞轻量探测帧 `{"type":"cmd","cmd":"ping"}` 或监听特征 `status` 心跳，自动锁定响应 NDJSON 协议的通信口；
  2. **手动指定与配置持久化**：
     - 在 Web 控制台设置抽屉中提供“串口选择”下拉列表（含“自动探测（推荐）”及所有已枚举 COM 口选项）；
     - 用户手动选定的端口自动持久化至 `gateway_config.json`，下次启动优先尝试历史成功端口。

### 7.2 验证码自动复制开关与防打扰规范（课题 2）
- **现象与设计意图**：
  当前上位机（Hub 与 Web）一旦提取到验证码短信，无条件毫秒级直写 Windows 系统剪贴板。该设计虽极致提速，但存在侵入性风险：若用户刚复制了一段核心代码或复杂长文本，突发短信会冲刷剪贴板导致用户原复制内容丢失；同时在投屏、远程会议或多设备剪贴板同步（如 Win+V 云同步）场景下存在隐私泄露隐患。
- **工程解法规范**：
  1. **配置项显式化**：在 `gateway_config.json` 引入 `system.auto_copy_otp`（布尔型，默认 `true`）；
  2. **前端交互与说明**：Web 控制台设置抽屉提供“⚡ 验证码自动写入系统剪贴板”切换开关，并附带体验说明：“开启后捕获验证码直接 Ctrl+V 即可粘贴；关闭后仍可随时点击短信卡片上的复制按钮手动取码”；
  3. **双端双向响应**：
     - 后端 `gateway_hub.py` 在执行 `set_windows_clipboard` 前核验配置项，若关闭则仅推送 Toast 提示而不写入剪贴板；
     - 前端 `web/index.html` 在 SSE 收到 `sms_received` 时，同样仅在开关激活时调用浏览器剪贴板 API。

### 7.3 实时数据流与前端渲染类型容错规范（课题 3）
- **现象与致命根因**：
  用户反馈“短信来了之后上位机好像不会自动刷新”。经排查定位到确切的隐蔽运行时崩溃：
  1. 板端 `sms_service.lua` 发送的实时事件包中，`time` 字段直接取了 `os.time()`（整型时间戳，如 `1726136800`）；
  2. `gateway_web.py` 在接收 `sms_rx` 并向 SSE 广播时，直接透传了该整型数字，未做格式化转换；
  3. `web/index.html` 的 `renderSmsList()` 在排序时执行 `tB.localeCompare(tA)`。当 `tB` 为整型数字时，JavaScript 抛出致命错误：`TypeError: tB.localeCompare is not a function`；
  4. 异常被外层 `catch (err) {}` 静默吞掉，导致 DOM 渲染彻底阻断，新短信无法展示，造成“无法自动刷新”假象。
- **工程解法规范**：
  1. **后端数据标准化**：`gateway_web.py` 在转发 `sms_rx` 时强制将时间字段标准化为 `YYYY-MM-DD HH:MM:SS` 格式字符串；
  2. **前端防御性转换**：`web/index.html` 所有时间比较强制使用 `String(tA || '')` 防御，避免非字符串调用 `localeCompare`；
  3. **禁止空 catch 吞异常**：显式打印控制台错误日志，保障数据流可观测性。

### 7.4 多设备接入架构设计（课题 4）
- **物理与操作系统事实**：
  多块 Air780EPV 同时通过 USB 接入电脑时，每块板子拥有独立的 USB 控制器与序列号，Windows 会分别枚举出独立的串口组（板A=COM6/7/8，板B=COM9/10/11）。彼此在物理层、电气层与操作系统驱动层完全隔离，天然支持同时并发通信，互不干扰。
- **多设备会话池架构演进（Device Session Pool）**：
  1. **多端口并发管理**：上位机 Hub 升级为设备会话池，为每个检测到的模组分别维护一个 `GatewayDeviceSession`，通过 SIM 卡 `ICCID` 或模组 `IMEI` 作为唯一硬件标识（Device ID）；
  2. **数据资产汇聚与打标**：短信入库与通知分发打上 `device_id` 与 `sim_slot` 标签（例如“卡1·联通 132****”、“卡2·移动 138****”）；
  3. **双模式 Web 界面**：
     - **聚合信息流（All-in-One）**：双卡/多卡短信按时间倒序混排，卡片标注来源设备专属色块；
     - **设备切换器**：顶栏支持切换当前控制的目标设备，独立查看该卡的信号 RSRP、温度、电压、RNDIS 网卡与 FOTA 升级状态。

### 7.5 硬件堆叠电气评估与最优工业拓扑（课题 5）
- **排针直通上下焊接之致命风险（坚决禁止）**：
  Air780EPV 两侧排针引出 `5V`、`V_GLOBAL_3V3`、`UART_TX/RX`、`PWRKEY` 等核心信号。如果直接点对点上下堆叠焊接：
  1. **电源反灌烧毁**：各板内部 DCDC/LDO 产生的 3.3V 存在微小工艺压差（如 3.31V 与 3.29V），直接直连会引发持续的无保护倒灌电流，烧毁电源芯片；
  2. **串口对地短路击穿**：若板 A 的 TX 与板 B 的 TX 短接，当两板逻辑电平相反时（高电平 3.3V 对 低电平 0V），将形成电源对地直通短路，击穿芯片 GPIO 推挽管；
  3. **按键控制丧失独立性**：PWRKEY 直通将导致两块板子强制同步开关机，无法单独复位。
- **最优工业级解法：带供电 USB 集线器 + 立式刀片卡架**：
  - **硬件构成**：采购工业级带独立 12V 供电的 4~7 口 USB Hub，每块 Air780EPV 采用超短直角 Type-C 数据线插入，搭配亚克力或 3D 打印立式卡架垂直插放；
  - **核心优势**：
    1. **零硬件修改**：保留所有开发板完整原生形态与质保，零短路风险；
    2. **独立热插拔**：更换任意 SIM 卡或单板烧录维护，其他板卡零中断运行；
    3. **高速 USB 隔离**：走 USB 2.0 原生独立总线中断，吞吐量远胜脆弱的板间低速 I2C/串口；
    4. **供电稳定充裕**：独立电源可轻松支撑多路模组同时发射时的高达 1A 峰值脉冲电流。

## 8. 宿主宽带代推优先与 Push ACK 超时降级容灾架构 (AIR-17)

### 8.1 架构设计背景与 0 流量保号防线
出厂状态下，网关遵循“0 流量纯信令保号”原则，板载蜂窝数据通信严格掐断（`mobile.data(mobile.CONF_CELLULAR_DATA, 0)`）。日常所有飞书、Bark、Webhook 推送均由宿主机（PC/NAS）通过本地宽带代推。
然而，若电脑休眠、断电或网关程序意外退出，新短信可能因宿主失联而无法送达。系统确立**“宿主宽带优先代推 + Push ACK 握手确认 + 5秒超时板端降级自推 + 离线黑匣子兜底”**的四级闭环：

### 8.2 双向握手与时序流转
1. **事件抛出**：板端收到新短信时，通过 VUART_0 物理串口向宿主机抛出主动推送帧：
   ```json
   {
     "type": "push",
     "event": "sms_received",
     "data": {
       "msg_id": "sms_1726160000_1234",
       "phone": "+8613800000000",
       "content": "【某某平台】验证码：123456",
       "otp": "123456",
       "time": 1726160000
     }
   }
   ```
2. **守候定时器挂起**：板端调用 `sys.timerStart(timeout_cb, 5000, msg_id)` 启动 5.0 秒软件看门狗，并置位待确认状态；
3. **宿主机宽带代推与回执**：
   - 宿主机 Hub 监听到 `sms_received` 事件后，立即通过本地局域网/宽带代发飞书 Webhook 或 Bark；
   - 无论代推成功与否，宿主机立即向物理串口回送专属 Push ACK 帧：
     ```json
     {"type": "push_ack", "event": "sms_received", "msg_id": "sms_1726160000_1234"}
     ```
4. **板端握手确认与定时器取消**：板端 `serial_comm.lua` 收到该 ACK 后，校验 `msg_id` 一致，立即调用 `sys.timerStop` 销毁定时器。全程未开启蜂窝数据，流量消耗为 0；
5. **宿主失联与板端降级自愈**：
   - 若 5.0 秒内未收到 ACK（宿主机离线），`timeout_cb` 被触发；
   - 板端自动执行“临时使能蜂窝数据（`mobile.data(mobile.CONF_CELLULAR_DATA, 1)`）➔ 驻网检查 ➔ 板端 HTTP 直推 Webhook ➔ 推送完成立刻切断蜂窝数据”的原子自愈流程，守住短信不丢失的高可用生命线。

## 9. 来电暗号拦截秒挂与七牛云空中热更新 FOTA 标准 (AIR-18)

### 9.1 来电暗号：0 话费纯信令拦截秒挂 (`call_service.lua`)
- **秒级拦截算法**：注册 `sys.subscribe("CC_IND", ...)`。基站呼入到达模组触发 `RING` 振铃状态时，微内核在毫秒级内直接调用 `cc.hangUp()` 切断通话；
- **0 话费保障**：呼叫尚未接通即被挂断，运营商基站无法建立计费会话，通话账单为 0 元；
- **暗号联动 FOTA**：比对呼入主叫号码，若匹配 `config.lua` 中预设的管理员白名单（`secret_caller`），板端自动触发静默 FOTA 升级任务。

### 9.2 七牛云空中热更新（FOTA）底层容器规范
板端基于七牛云华东 CDN（`z0` 空间，域名 `http://raw-fota.air780epv.luat.com.cn` 或配置镜像源）执行免插线固件热更新：
- **92 字节标准 LuatOS OTA 头部**：
  LuatOS 底层 C 固件拒绝直接刷写纯文本 Lua 压缩包。升级镜像（`update.bin`）前 92 字节必须填充标准二进制头：
  - Magic 标识（4 字节，如 `0x54414F4C` 即 `LUAT`）；
  - 硬件平台识别码（EC718PV / EC618）；
  - 固件版本号与镜像长度；
  - CRC32 校验和与数字签名占位。
- **LZMA SOTA 压缩容器**：
  核心代码段采用 LZMA 算法高压缩比封装，确保升级包体积被严格压缩在 Flash OTA 预留扇区（< 32KB）之内；
- **上位机构建发布流水线 (`tools/fota/publish_ota.py`)**：
  自动读取 `deploy/smart-gateway-780epv/` 下各 Lua 源码，调用原生 LuaDB 打包器生成紧凑二进制，注入 92B Header 与 LZMA 容器，计算 SHA256，生成 `version.json`，并一键推送到七牛云对象存储空间。

## 11. 串口自适应动态探测与热拔插漂移自愈机制

### 11.1 串口漂移痛点与根因
模组在复位、烧录固件或拔插后，Windows USB 枚举可能将端口由 `COM8` 漂移至 `COM16`（或者 `COM6` 漂移至 `COM15`）。若上位机硬编码串口号，将导致服务瘫痪。

### 11.2 动态特征探测引擎 (`find_cellular_vuart_port`)
上位机通过 `serial.tools.list_ports.comports()` 读取系统枚举树，匹配物理拓扑：
1. **硬件 ID 圈定**：匹配 `VID:PID == 19D1:0001`（合宙/移芯复合设备）；
2. **接口拓扑精准过滤**：
   - 过滤 `LOCATION` 包含 `x.4` 的 Trace 调试口（避免非文本二进制流使程序崩溃）；
   - 过滤 `LOCATION` 包含 `x.2` 的 AT 口；
   - 锁定包含 `x.6` 或 `MI_06` 的 **VUART_0 用户口**（无论其被系统重命名为 COM8 还是 COM16）。
3. **断线热扫描自愈**：
   Hub 主循环捕获 `SerialException` 后，立即释放句柄并以 1.5 秒为周期循环重试探针。设备重新插入后秒级重新建链，上层 SSE 推流与 Web 客户端完全透明无感。

## 12. 黑匣子三层防 OOM 游标分页与前端触底无感懒加载

### 12.1 连续刷新导致的板端 OOM 重启根因
Air780EPV 板载 Lua 堆内存上限仅 128KB。当脱机黑匣子积累数十条短信时，若上位机 Web 控制台并发或连续刷新，板端连续执行全量 JSON 序列化将瞬间耗尽可用堆（OOM），引发芯片硬件看门狗硬重启。

### 12.2 三层游标分页架构
- **板端游标协议**：
  游标设计为 `h:<generation>:<offset>`（如 `h:36:15`）。板端每次最多切片返回 15 条记录，单条正文强力截断至 256 字节，内存峰值恒定控制在 12KB 以内；
- **后端有效性清洗防御 (`gateway_web.py`)**：
  前端 Web 页面由于异步竞争可能传进 `"0"`、`"null"`、`"undefined"` 等非预期游标。后端在调用 Hub 之前进行正则白名单校验：仅格式合法的游标透传给板端，非法游标一律清洗为空（按首屏最新 15 条处理），彻底避免板端正则匹配失败报 `CURSOR_STALE` 甚至崩溃。

### 12.3 前端无感懒加载双保险设计
- **触发感知**：收件箱底部挂载 `#smsSentinel` 哨兵节点，通过 `IntersectionObserver` 配合 `rootMargin: '160px'` 预先拉取；
- **确定性判定三步法**：
  1. 优先校验后端显式返回的 `has_more` 布尔值；
  2. 其次校验 `next_cursor` 是否非空；
  3. 再次比对 `total > 当前卡片数`；
- **零增量死循环熔断**：非首屏请求下，若拉取到的增量短信数量为 0，立即熔断置 `smsHasMore = false` 并展示“已加载全部脱机记录”，彻底消除网络死循环风暴。

## 13. Windows 独立桌面 Exe 与宿主系统原生整合规范

### 13.1 单文件便携分发构建 (`build_exe.py`)
使用 PyInstaller 配合 UPX 压缩，将 Python 运行时、Pyserial、Web 静态资产（HTML/CSS/JS/图标）整合打包为单文件 `Air780EPV-Gateway.exe`（体积约 27.2MB）。

### 13.2 Windowed 模式流保护 (`_SafeStream`)
在 `--windowed` / `--noconsole` 模式下，Windows 不为进程创建控制台终端，`sys.stdout` 和 `sys.stderr` 被置为 `None`。任何调用三方库抛出 `print()` 或 `logging` 的行为都会引发 `AttributeError: 'NoneType' object has no attribute 'write'` 导致崩溃。
**架构防御**：程序入口强制注入 `_SafeStream` 虚拟哑对象，重写 `BaseHTTPRequestHandler.log_message`，杜绝任何静默崩溃。

### 13.3 单实例互斥与原生 App 窗口唤起 (`gateway_app.py`)
- **Win32 内核互斥体**：使用 `CreateMutexW(None, True, "Air780EPV_Gateway_Desktop_App_Mutex")`。新启动实例若检测到 `ERROR_ALREADY_EXISTS`，自动唤起已运行实例的前端窗口并静默退出，严禁两个进程竞争同一个物理串口；
- **Edge / Chrome 原生 App 模式**：通过调用系统已安装浏览器：
  ```bash
  msedge.exe --app=http://127.0.0.1:17801 --window-size=1280,820 --app-id=Air780EPVGateway
  ```
  呈现无地址栏、无多余标签页的原生独立桌面软件质感；
- **系统托盘驻留**：基于 `pystray` 提供托盘图标、设备连接状态显示、一键打开控制台与安全退出选项。

## 14. 系统全生命周期“开箱即用（Running & Opened）”交付硬性标准

为确保系统面向人类用户提供无缝的交互体验，工作区确立如下硬性交付准则：
1. **测试完毕绝不留空关停**：
   在自动化回归验收（如 `test_exe_live.py`）执行完毕后，严禁将服务进程停留在杀死/关闭状态。必须在收尾脚本中自动以独立进程组拉起 `Air780EPV-Gateway.exe`；
2. **前端界面主动唤起打开**：
   汇报交付结果前，上位机必须通过系统调用重新打开或激活 Edge 原生 App 窗口（`http://127.0.0.1:17801`）；
3. **交付状态确定性**：
   用户切回电脑屏幕时，直接面对的必须是一个“端口 17800/17801 正常就绪、板端硬件正常同步、控制台界面处于前台且立即可操作”的活体应用，杜绝任何 `ERR_CONNECTION_REFUSED` 异常。

## 15. GitHub 公开开源与无痕发布流水线规范

针对将私有大仓子模块独立发布为 GitHub 公开开源项目的场景，架构确立“单源开发 + 瞬时推流 (Ephemeral Pipeline)”规范：
1. **单源开发无冗余**：坚决不在本地磁盘创建或长期维护任何 `output/` 副本，杜绝代码修改不同步与双重维护隐患；
2. **瞬时无痕推流**：借助 `tools/publish_to_github.py`，在操作系统临时空间（`%TEMP%`）中瞬时完成白名单抽取、脱敏安全门禁检测并直接推送到 GitHub，任务完成后临时环境自动销毁；
3. **脱敏安全门禁 (Security Gate)**：自动阻断一切真实手机号、Webhook、云存储 AK/SK 与本地绝对路径；
4. **二进制与源码分治**：27MB 独立桌面应用 `Air780EPV-Gateway.exe` 走 GitHub Releases 独立附件分发，Git 树仅保留纯净源码与工程规范。

详细规范参见：[`specs/open-source-release-guide.md`](open-source-release-guide.md)。

## 16. 硬件未接入/离线状态防震荡与 Fast-Fail 机制 (AIR-15 缺陷根治)

针对上位机在未插入 4G 短信棒时出现的“已连接 / 已断开”红绿 Toast 震荡、4000ms 挂起超时与假在线缺陷，系统落地端到端全链路闭环架构：

### 16.1 根因剖析与防御时序
1. **中枢无阻塞 Fast-Fail 机制**：
   - 传统逻辑在物理串口未打开时直接丢弃客户端下发的命令，导致 Web 层等待 RPC 响应直至 4.0 秒硬超时；
   - 修复后：中枢 `gateway_hub.py` 在串口未连接或离线时，立即向客户端回送 `{"type": "response", "id": req_id, "ok": false, "online": false, "error": "4G 短信棒未插入或物理串口已断开"}`，请求在 0~1ms 内极速返回，杜绝 Web 服务端线程阻塞。
2. **状态快照严格清洗与归零**：
   - 物理串口断开或未接入时，Hub 与 Web 两级内存缓存的工况数据（CSQ、RSRP、温度、供电、运行时间等）强制清洗为初始占位符，且核心元数据坚决标注 `"online": false`；
   - 杜绝向 Web 前端下发残留旧快照，彻底消除了旧快照伪装在线与看门狗判定打架的死循环。
3. **前端状态机确定性判定**：
   - 前端 `renderStatus()` 升级为强类型断言，仅当 `data.online === true` 时才允许切为在线态；
   - 设备切为离线态时立即将 `state.lastHeartbeatTime` 彻底清零，杜绝因异步心跳轮询回包导致时序倒流；
   - 优化断开 Toast 策略：仅当此前明确处于在线状态（`wasOnline === true`）时才弹出断开红框，初次打开或持续未插入状态静默保持离线，零假连接干扰。
